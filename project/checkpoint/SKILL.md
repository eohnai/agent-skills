# Checkpoint

## Overview

Write down where the project stands so the next session (yours or an agent's) can pick it up cold. Record judgment and evidence; derive everything else.

## Finding the records

Same rule as `catch-up`: `./STATUS.md` → records folder is `.`; else `./docs/STATUS.md` → `docs/`. If neither exists, ask whether this is a workspace (create at root) or a single repo (create in `docs/`), then create STATUS.md from the template below.

## Steps

1. Review what happened this session: the conversation, `git status`, `git diff --stat`, and commits since the last STATUS.md log entry.
2. Update STATUS.md to match the template. Rewrite **Now**, **Next**, and **Blockers** to be current; don't append to them.
3. **Verification**: list the exact commands run this session and their results (pass counts, exit codes, errors). If nothing was run, write `Not verified this session.` Never write "tests pass" without a command and result from this session.
4. **Progress**: tick off the tasks completed this session in the specs themselves (see the `progress` skill for the convention). Then run the `progress` script and replace the Progress section of STATUS.md with its table. Don't keep a second copy of the task list.
5. Append one dated entry to **Log**.
6. **Stale records**: if a spec or older note contradicts the code, list it under Blockers as `Stale: <file>: <what the code actually does>`. Change the spec only if the user agrees.
7. If a choice between approaches was made this session and has no decision record, say so and offer to run `record-decision`.
8. Show the user a short summary of what changed in STATUS.md. Do not commit; the user commits.

## STATUS.md template

```markdown
# Status

## Now
What is being worked on and its current state (2–4 lines).

## Next
1. Concrete next action (file or command to start from)
2. ...

## Blockers
- None

## Progress
_Generated by the progress script at checkpoint; don't edit by hand._
| Spec | Status | Done | Left | Next task |
|---|---|---|---|---|

## Verification
- `<command>`: <result> (YYYY-MM-DD)

## Log
- YYYY-MM-DD: what got done, in one or two lines. Newest first.
```

## Common mistakes

- Logging intentions as progress ("implemented X" when X was only started).
- Copying the spec's task list into STATUS.md, where it goes stale.
- Leaving an old Verification entry in place as if it still held after code changed.
